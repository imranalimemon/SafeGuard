# SafeGuard AI — Machine Learning, Violations & Alerts

## Overview
This document covers the core intelligence of SafeGuard AI: the YOLOv8 detection pipeline, the logical rules for determining safety violations, and the notification system that triggers alerts when violations occur.

## Machine Learning Pipeline (`backend/detection/`)

### Model Execution (`model.py`)
SafeGuard uses the **YOLOv8 (You Only Look Once, version 8)** model provided by Ultralytics for real-time object detection.
- **Initialization:** The model weights (`yolov8s.pt` or a custom trained `.pt` file) are loaded into memory on startup.
- **Inference:** Images (from uploads or video streams) are processed using OpenCV (`cv2`) and passed to the YOLOv8 model.
- **Output:** The model returns a list of detections, including bounding box coordinates (x1, y1, x2, y2), class IDs (Person, Helmet, Vest), and confidence scores.

### Violation Logic (`violation_logic.py`)
Once objects are detected, the system applies logical rules to determine if a violation has occurred.
- **Intersection over Union (IoU):** The system uses bounding box overlap (IoU) to associate PPE (helmets, vests) with specific persons. If a helmet's bounding box significantly overlaps with a person's bounding box, that person is considered to be wearing a helmet.
- **Configuration Parsing:** The logic module queries the database (`AlertSettings`) to check current rules (e.g., `confidence_threshold`, `require_helmet`, `require_vest`).
- **Evaluation:** If a person is detected but the required PPE is *not* associated with them, a violation is flagged.

### Annotation (`annotator.py`)
Visual feedback is generated by drawing on the original image:
- Bounding boxes are drawn around detected persons and PPE.
- If a person is compliant, their box is drawn in green (Compliant).
- If a person is missing required PPE, their box is drawn in red (Violation), and text is overlaid specifying what is missing (e.g., "Missing: Helmet").
- The annotated frame is then saved to disk or broadcast over WebSockets.

## Alert System (`backend/alerts/`)

When a violation is detected and saved to the database, the backend triggers the `AlertManager`.

### Throttling & Cooldowns (`throttle.py`)
To prevent spam, alerts are subject to cooldown periods configured in the database settings.
- The system keeps track of the last time an alert was sent for a specific channel (Email or WhatsApp).
- If a new violation occurs within the cooldown period (e.g., 300 seconds), the alert is suppressed.

### Email Integration (`email_service.py`)
- Uses Python's native `smtplib` and `email.mime` modules.
- Constructs an HTML email detailing the violation type, timestamp, and a summary of missing PPE.
- Uses credentials (`SMTP_SERVER`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`) from the `.env` file.

### WhatsApp Integration (`whatsapp_service.py`)
- Typically integrates with the Twilio API (or a similar provider) for sending WhatsApp messages.
- Uses `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, and `TWILIO_WHATSAPP_NUMBER` from the `.env` file.
- Sends a concise text alert summarizing the incident to the configured recipient number.

### Alert Flow
1. `model.py` detects an infraction.
2. The API route saves the `Violation` to the DB.
3. `AlertManager.trigger_alerts(violation, settings)` is called asynchronously.
4. `throttle.py` verifies cooldowns.
5. If allowed, `email_service` and/or `whatsapp_service` dispatch the payloads.
